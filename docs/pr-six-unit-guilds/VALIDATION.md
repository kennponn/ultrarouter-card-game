**基线结果的解释。** 原始上游有两项过时测试准备／预期，在 SQLite、MySQL、PostgreSQL 均复现：补给测试仍要求体力立即增加，但原版本实际寄送邮件；培养测试使用一级船长，已达到伙伴等级上限，却要求继续喂书。共 6 个叶子测试、连同父节点计 10 个失败节点。该原始结果保留于[基线节点清单](data/baseline-test-nodes.json)。本次补给改为直接到账；培养测试明确准备 60 级船长，继续检查真实材料消耗和重试不重复扣款。

CI 对基线只接受上述精确失败集合，出现任何其他失败、缺少数据库、编译失败或跳过测试都会失败。本次候选版本要求 **零失败、零跳过**，没有沿用基线例外。旧分支专用的两个 workflow job 因分支条件不启动；本次真实三库由 `six-unit-compatibility` 完整执行。

## 2. 真实旧版本 → 新版本升级

先运行不可变上游代码，创建账号、实际兑换礼包、保存公会与未结算战斗；随后在**同一个数据库**启动新代码。没有用新版本序列化对象冒充旧存档。

实际数据库版本为 SQLite 3.41.2、MySQL 8.0.46、PostgreSQL 16.15；日志记录了每种引擎的版本查询结果。CI runner 的硬限制为 2 CPU，未使用未受限的并行编译或测试容器。

| 数据集 | SQLite | MySQL | PostgreSQL | 合计 |
| --- | ---: | ---: | ---: | ---: |
| 旧账号 | 96 | 96 | 96 | 288 |
| 未完成的旧公会 Boss | 24 | 24 | 24 | 72 |
| 尚未结算的旧战斗 | 12 | 12 | 12 | 36 |
| 更新前已寄出的礼包附件 | 96 | 96 | 96 | 288 |
| 旧四人编队扩为六人后保存 | 96 | 96 | 96 | 288 |

![同库升级样本](https://1810551251.github.io/ultrarouter-card-game-screenshots/six-unit-guilds-20261127/15-database-upgrade.png)

每个账号逐项比较 14 个序列化字段：编队、伙伴（含装备／佩戴铭刻）、金币、体力、代币、双倍卡、材料、宝石、芯片、铭刻、奇物、通关、星级、邮箱；字段必须实际存在。额外比较宿主钱包余额，检查重复加载不改变资产。样本包含不同数量的宝石、奇物和不同品质的已佩戴铭刻。

- 旧公会剩余生命按比例向上取整映射至新 Boss：`ceil(旧剩余生命 × 1,300,000 / 24,000)`；个人实际累计伤害保持原值，不伪造新增贡献。
- 旧战斗退出后重复结算返回同一结果，金币不增加；新建请求也不能把撤退当作胜利。
- 旧礼包附件首次领取金币增加 300；同请求重试返回原回执；换请求 ID 重领被拒；重新兑换同一礼包被拒。
- 六人编队顺序与提交顺序完全相同。

[升级统计与原始语料哈希](data/upgrade-statistics.json)；原始 JSONL、合成语料和实验数据库保存在 CI artifact，游戏仓库只收录统计、源码哈希、逐测试结果与复跑程序。

## 3. 公会 Boss 强度：真实 Go 战斗结果

直接调用生产 `simulateGuildRaid`，不以简化伤害公式替代战斗。覆盖 27 个「培养档位 × 队伍强度 × Boss 阶段」组合，每组 96 个固定种子，六种周元素，分别从满血和 45% 生命开始。高阶队伍另覆盖前四个 Boss。

每场检查六位己方、回合不超过 20、伤害不超过 Boss 当前生命、事件编号连续、生命／护盾非负、怒气在 0～100。共检查 **382,396 个战斗事件**。

| 档位 | 伙伴等级 | 星级 | 专武等级 | 突破阶 | 各项努力值 | 三技能等级 | 觉醒阶 | 组织成员数 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 20 | 2 | 0 | 1 | 80 | 5 | 0 | 8 |
| 2 | 40 | 3 | 3 | 2 | 400 | 15 | 0 | 15 |

阵容按坦克、治疗、双输出和两名补位随机抽取，不重复角色；早期限定 R／R+SR 池。星级不低于角色基础星级，高星觉醒满足最低门槛。偏弱组在等级、星级、专武、努力值和技能上降低投入；偏强组提高投入，具体幅度见[采样程序](harness/balance_test.go.example)。

## 6. 合并与发布边界

以 `git merge-tree --write-tree` 验证上游基线和候选分支，合并树等于候选树，无冲突。28 位角色除图片／演出字段以外的配置逐项相同；56 张角色原图与透明图逐文件 SHA256 相同。资源重排是目录移动，PR 截图和测试图表全部外链。

## 7. 复跑

后端完整实验，在支持 Docker 的 Linux 测试机执行：

```sh
mkdir -p .local/six-unit-evidence
sh scripts/build-half-cpu.sh --run --rm -e GOMAXPROCS=1 \
  -v "$PWD:/src:ro" -v "$PWD/.local/six-unit-evidence:/out" \
  ubuntu:24.04 sh /src/docs/pr-six-unit-guilds/harness/run.sh
```

使用 Go 1.25.5，下载包 SHA256 对照官方清单；所有构建／测试受共享 wrapper 硬限制至宿主最多一半 CPU，串行执行 `go test -p 1 -parallel 1`。不会修改生产服务的 CPU 配置。

前端和发布检查：

```sh
python scripts/sync-catalog.py --check
python -m unittest discover -s tests -p 'test_*.py'
python scripts/audit-release.py
sh scripts/build-half-cpu.sh --run --rm -v "$PWD:/workspace" -w /workspace \
  node:24-bookworm-slim sh -c 'npm ci --ignore-scripts && npm test'
```

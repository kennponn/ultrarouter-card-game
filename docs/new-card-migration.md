# 从战斗系统迁移成品卡的标准流程

适用于将独立战斗系统中已经完成并验证的卡迁入本游戏。以 `xs039` 解弦川为首个实例。卡牌 JSON 和图片能导入，不代表技能已经接入服务端结算。

## 1. 固定来源与实现边界

1. 记录来源 `card.json`、运行资源、引擎及测试的版本和 SHA-256；备份目标项目与需要合并项目的所有现有改动。使用独立发布分支或 worktree，保留原目录的未提交状态。
2. 对照开发记录、引擎和测试，把普通攻击、小技能、必杀、被动、初始星级、高星设计逐项列成验收表。区分“文字设定”“已实现”“已测试”，不能把 proposal 当成生效规则。
3. 确认卡 ID 唯一、资源来源、获取渠道和首次投放日期。故事提到的未来角色不是可用卡，不能凭引用创建整卡或激活羁绊。

解弦川的来源实装边界是初始 5 星。8／11 星专属规则和星霜演化仍为设计预览；通用培养沿用本游戏现有体系。此边界需同时出现在图鉴、验证报告和 PR。

## 2. 导入唯一目录源

- 将卡定义放入 `content/cards/<id>/card.json`，在 `content/cards/index.json` 中登记。仅复制运行需要的立绘、战斗切图和技能 WebP；开发草图、录屏、验收截图不进入运行图片库。
- 保留相对资源路径，逐项比较复制前后的 SHA-256。新增特效目录时同步检查预览服务器和发布白名单，防止开发目录能打开、正式包却漏图。
- 配置 `sources`、重复卡转换数量、初始星级和档案。获取途径必须指向本游戏实际提供的入口。
- 执行 `python scripts/sync-catalog.py`，由目录源生成 `js/data.js` 与 `backend/model/gacha_catalog.json`。随后执行 `python scripts/sync-catalog.py --check`。不要只手改生成文件。
- 检查培养配置：专武、定位、羁绊与已有奖励限制。旧卡固定配对测试继续保留，新卡只能激活已经发布并配置的关系。

## 3. 服务端实现规则

先核对字段能否被 Go 类型读取，再逐条迁移语义。未知机制应由目录校验拒绝，不能静默回退成普通卡。

| 核对项 | 验证要求 |
| --- | --- |
| 初始星级与成长 | 碎片合成和整卡发放均读取卡的初始星级；来源已含初始星级的数值不得再乘一次星级成长；前后端展示一致 |
| 六维属性 | 特攻／特防真正进入伤害结算；旧卡缺少字段时保持原规则；培养加成有一致换算 |
| 资源与冷却 | 明确初始值、上限、消耗时点、行动／回合计时、额外行动与控制状态的边界 |
| 目标与阵型 | 排／列、最高攻击、最低血比、平局次序明确；换位仅改变战斗位置，不改变账号编队 |
| 效果组合 | 护盾、暴击、减伤、无敌、技能无效、净化、持续伤害、反伤、致命救助、多段与死亡连锁均有测试 |
| 双方与多波 | PvP 两边都可用；资源与施法者归属隔离；切波不能丢失该保留的状态 |
| 状态存储 | 战斗临时状态留在战报，按事件深复制；账户不接受浏览器提交的血量、资源、站位或奖励 |

以来源确定性用例核对固定数值，再加入真实战斗多种种子回归。先解释失败来自产品代码还是夹具假设，再修复；不可删除断言让检查变绿。

## 4. 配置获取渠道与轮换

强者世界使用 `backend/model/gacha_world.json` 的 `rotations` 显式名单。新增一个按周一起始、日期递增的配置版本，名单内必须是合法且允许 `world` 来源的 SSR，拒绝空名单和重复项。不再通过“所有 SSR”自动推导卡池。

已持久化的赛季继续使用原英雄与规则，往期积分箱和排名奖励不能改发新卡。验证生效周前后、完整循环、非法配置、周末关闭、旧奖领取和重复请求。界面从服务端读取本期英雄、轮换名单与下期预告。

碎片到阈值后，由玩家在图鉴发起合成，服务端扣片并授予初始星级，确认回包后才进入编队。覆盖少一片、刚好足量、重复请求、并发、失败回滚和重新加载。

## 5. 图鉴与战报播放器验收

图鉴核对卡数、搜索、技能、档案、图片、获取跳转及未实装说明。浏览器必须实际点击获取、抽取、合成、编队与开战，检查桌面、手机和横屏布局、404 与脚本错误。

服务端战报应带有可区分的技能键、技能名、分支、被动标识及完整状态快照。复用现有战斗播报、立绘切入与日志；新技能贴图只承担演出，不能在浏览器计算效果。新增站位字段须兼容旧战报，校验全队位置唯一后整体更新。

使用 Go 生成的原始战报验收普攻、小技能两个分支、必杀切入、被动日志、换位、暂停、单步、倍速、跳过、刷新恢复及最终血量。纯演出预览不能作为技能结算通过的证据。

## 6. 合并与数据库验收

合并其他工作目录时逐项比较双方差异，记录独立功能导入与重叠行为的取舍。尤其检查重复字段、宿主 JSON 类型、旧奖励入口、旧在途战斗和旧赛季配置。

在兼容的临时宿主中运行模型和控制器测试，分别连接真实 SQLite、MySQL、PostgreSQL。包括全新建库、重复迁移无 DDL、同一数据库从固定旧版本升级、数据资产不丢失、旧在途战报结算、幂等、并发与事务回滚。JSON 字段使用宿主约定的 `GachaDocument`，行锁复用已有跨方言帮助函数。

完整宿主账号、认证、钱包与数据库适配器不随游戏发布。集成测试夹具须明确为合成适配环境；不能据此声称任意生产宿主已验证。

构建和 CPU 密集测试只能经共享硬限额包装器运行，总计不超过服务器一半 CPU：

```sh
sh scripts/build-half-cpu.sh --run --rm -e GOMAXPROCS=1 \
  -v "$PWD:/src:ro" -v "$PWD/../game-evidence:/out" \
  ubuntu:24.04 sh /src/docs/pr-six-unit-guilds/harness/run.sh
```

输出目录先创建。共享宿主通过私有环境的 `GACHA_BUILD_WRAPPER` 指定共享包装器绝对路径；不得发布宿主私有路径。容器内 Go 测试固定 `GOMAXPROCS=1 go test -p 1 -parallel 1`，不得另起未受限任务。线上服务不套该构建限制。

## 7. 证据、说明与提交

1. 保存测试源码提交 SHA、运行链接、各层计数、数据库版本、失败与修复原因。将旧基线的已知失败单独列出；新候选必须无未解释失败、无漏跑。浏览器模拟账号、真实服务端战报和真实数据库测试分别说明。
2. 截图上传独立图床／截图仓库，以固定提交 URL 引用。游戏仓库仅保留图片索引、SHA-256 和文字说明，不放验收 PNG。
3. 运行目录同步、发布隐私／白名单审计和差异检查；只提交游戏代码、运行素材、集成示例与必要文档。不要输出凭据或发布私有配置。
4. PR 描述先写玩家行为、修复和验证结果，再写接入边界。若聚合多个未合并 PR，明确列出覆盖关系，告知维护者只需合并当前 PR；提交前确认上游基线与已有差异完整包含。
5. 最后一次代码修改必须由相应检查验证。测试通过后仅新增文字证据可说明与已测代码的关系。部署前另行备份并比较目标哈希，静态资源更新无需重建后端，但新增服务端技能需要更新游戏后端。
